# Parsing JSON & JSON Lines for RAG — JSONLoader with jq, and Custom Flattening

This folder covers loading **JSON** (`.json`) and **JSON Lines** (`.jsonl`) data into LangChain `Document` objects, which is the first stage of a RAG pipeline. The notebook compares two ways to turn nested JSON into text that an embedding model can search:

1. **`JSONLoader`** (LangChain) with a **`jq_schema`**: a query picks out the parts of the JSON tree you want, and each match becomes one Document.
2. **Custom JSON processing**: plain Python walks the JSON and writes each record out as readable, labelled text with metadata you design yourself.

├── files/
│   ├── company_data.json    # Sample input: nested company data (generated by the notebook)
│   └── events.jsonl         # Sample input: 3 event records, one JSON object per line (generated by the notebook)

## 1. Core Concepts

### RAG (Retrieval-Augmented Generation)
**Definition:** A technique where a Large Language Model (LLM) answers questions using information *retrieved* from your own documents, rather than relying only on what it learned during training.

**Explanation:** A RAG pipeline usually has these stages:

```
.json / .jsonl ──► Parse ──► (Chunk) ──► Embed ──► Vector DB ──► Retrieve ──► LLM answer
                  └ this folder ┘
```

JSON is very common in RAG sources: API responses, database exports, logs, product catalogues, chat histories and config files are all usually JSON. Before any of it can be embedded, it has to be turned into `Document` objects.

### JSON (JavaScript Object Notation)
**Definition:** A plain-text format for structured data, built from two container types and a few value types:

| JSON type | Looks like | Python type after `json.load` |
|---|---|---|
| object | `{"name": "John"}` | `dict` |
| array | `["Python", "SQL"]` | `list` |
| string | `"In Progress"` | `str` |
| number | `25`, `99.99` | `int` / `float` |
| boolean / null | `true`, `null` | `True` / `None` |

**Explanation:** Objects and arrays can be put inside each other to any depth, so JSON is a **tree**. The sample file `files/company_data.json` looks like this:

```
company_data.json
├── company: "TechCorp"
├── employees: [ ... ]                  ← array of 2 objects
│   ├── { id, name, role,
│   │     skills: [ ... ],              ← array of strings
│   │     projects: [ {name, status} ]} ← array of objects (3 levels deep)
│   └── { ... }
└── departments: { ... }                ← object of objects (keyed by name, not a list)
    ├── engineering:  { head, budget, team_size }
    └── data_science: { head, budget, team_size }
```

### Why JSON is hard to put straight into RAG
**Definition:** JSON is **semi-structured** data. Every value gets its meaning from its **path** in the tree (`employees[0].projects[1].status`), not just from the value itself.

**Explanation:** This is the same problem as with tables (see [ParsingCSV](../ParsingCSV/readme.md)), but with more levels. The value `"Completed"` means nothing on its own. It only means "*John Doe's* project *Data Pipeline* is completed" because of where it sits in the tree. So when you turn JSON into Documents, three questions decide the quality of retrieval:

1. **What is one Document?** The whole file, each employee, each project, each department?
2. **How much parent context goes with it?** If a project becomes its own Document, does it still say *whose* project it is?
3. **What is the text format?** Raw JSON (`{"name": ...}`) or readable text (`Name: John Doe`)?

| Granularity | Good for | Weak at |
|---|---|---|
| **Whole file = one Document** | Tiny files | Anything bigger than one chunk; retrieval becomes all or nothing |
| **One entity = one Document** (both methods here, per employee) | Questions about one entity: *"What skills does Jane have?"* | Questions across entities: *"Who works on projects that are In Progress?"* |
| **One leaf record = one Document** (e.g. each project) | Very precise matches | Loses parent context unless you copy it in (see Section 4) |

### Raw JSON text vs readable text
**Explanation:** Embedding models are trained mostly on natural language. Raw JSON works, but it fills the text with brackets, quotes and key syntax, and the keys carry meaning only by convention. Compare the two `page_content` values produced by the notebook for the same employee:

```text
# Method 1 (JSONLoader, raw JSON)
{"id": 1, "name": "John Doe", "role": "Software Engineer", "skills": ["Python", "JavaScript", "React"], "projects": [{"name": "RAG System", "status": "In Progress"}, ...]}

# Method 2 (custom, readable text)
Employee Profile:
Name: John Doe
Role: Software Engineer
Skills: Python, JavaScript, React
Projects:
- RAG System (Status: In Progress)
- Data Pipeline (Status: Completed)
```

The second version reads like a document, has a clear label ("Employee Profile") that says what it is about, and turns cryptic keys into plain words. It usually gives better embeddings and is easier for the LLM to quote in its answer.

### JSON Lines (`.jsonl`)
**Definition:** A text file where **each line is one complete JSON value** (usually an object), with no surrounding array and no commas between lines.

**Explanation:** This is the usual format for logs, event streams and dataset exports, because:
- You can **append** a record without rewriting the file (a normal JSON array would need its closing `]` moved).
- You can **stream** it line by line without loading the whole file into memory.
- One broken line does not break the rest of the file.

Here is `files/events.jsonl`. Note that records do not need the same keys (`page` and `amount` only appear on some lines):

```json
{"timestamp": "2024-01-01", "event": "user_login", "user_id": 123}
{"timestamp": "2024-01-01", "event": "page_view", "user_id": 123, "page": "/home"}
{"timestamp": "2024-01-01", "event": "purchase", "user_id": 123, "amount": 99.99}
```

For RAG, each line is already a natural Document boundary.

### jq
**Definition:** `jq` is a small query language (and command-line tool) for selecting and transforming parts of a JSON document. LangChain's `JSONLoader` uses the Python **`jq`** package to run the `jq_schema` you give it.

**Explanation:** A jq expression is a **path** through the tree. The `[]` operator means "for each element", and every value the expression produces becomes **one Document**. The patterns you need most often, run on `company_data.json`:

| `jq_schema` | What it produces | Documents |
|---|---|---|
| `.` | The whole file as one value | 1 |
| `.company` | `"TechCorp"` | 1 |
| `.employees[]` | Each employee object (used in the notebook) | 2 |
| `.employees[].name` | `"John Doe"`, `"Jane Smith"` | 2 |
| `.employees[].projects[]` | Each project object, across all employees | 4 |
| `.departments \| to_entries[]` | `{"key": "engineering", "value": {...}}` for each department | 2 |

> **Note:** `departments` is an *object keyed by name*, not an array, so `.departments[]` would return the inner objects but lose the names `engineering` / `data_science`. `to_entries` turns each key-value pair into a `{key, value}` object so the department name is kept.

### Document (LangChain)
**Definition:** `langchain_core.documents.Document` is LangChain's basic unit of data. It has two fields:
- `page_content`: the text that gets embedded and searched (a `str`)
- `metadata`: a `dict` of extra information (source file, record number, IDs, …)

**Explanation:** Both methods in the notebook return a `List[Document]` with **2 Documents** (one per employee). What differs is what goes into each field:

| | `page_content` | `metadata` |
|---|---|---|
| `JSONLoader` | Raw JSON string of the employee | `source`, `seq_num` only |
| Custom function | Readable "Employee Profile" text | `source`, `data_type`, `employee_id`, `employee_name`, `role` |

### `page_content` vs `metadata` for JSON
**Explanation:** JSON records are full of fields, so you have to decide where each one goes:

- **`page_content`** is what the embedding model "reads". Put the fields you want to *match on meaning* here: names, roles, descriptions, skills, project names.
- **`metadata`** is not embedded. Put fields used for **exact filtering** (`role == "Data Scientist"`, `employee_id == 2`), for citations (`source`), or for linking back to the original record (IDs) here.

A field can, and often should, go in **both** places. The custom function in the notebook puts `name` and `role` in the text (so a search for "data scientist" matches) *and* in metadata (so you can filter on them exactly).

### Cell 7: Method 1, `JSONLoader` with `jq_schema`

```python
from langchain_community.document_loaders import JSONLoader

employee_loader = JSONLoader(
    file_path='files/company_data.json',
    jq_schema='.employees[]',  # jq query to extract each employee
    text_content=False         # Get full JSON objects
)

employee_docs = employee_loader.load()
print(f"Loaded {len(employee_docs)} employee documents")
print(f"First employee: {employee_docs[0].page_content[:200]}...")
```

**How it works:**
1. `JSONLoader` reads the file and parses it.
2. It runs the jq expression `.employees[]`. The `[]` loops over the array, so it produces **one value per employee**.
3. Each value becomes a `Document`. Since the value is a dict, `text_content=False` tells the loader to turn it into a string with `json.dumps` and use that as `page_content`.

**Output:**

```text
Loaded 2 employee documents
First employee: {"id": 1, "name": "John Doe", "role": "Software Engineer", "skills": ["Python", "JavaScript", "React"], "projects": [{"name": "RAG System", "status": "In Progress"}, {"name": "Data Pipeline", "status"...
```

and each Document looks like:

```python
Document(
    metadata={'source': 'C:\\MyCode\\RAG\\JSONParsing\\files\\company_data.json', 'seq_num': 1},
    page_content='{"id": 1, "name": "John Doe", "role": "Software Engineer", ...}'
)
```

- **`source`**: the absolute path of the file.
- **`seq_num`**: the position of the record among the jq results, **starting at 1**.

#### Why `text_content=False` is needed here
By default (`text_content=True`) `JSONLoader` expects the jq result to already be a **string**. Each employee is an object, so without the flag `load()` fails:

```text
ValueError: Expected page_content is string, got <class 'dict'> instead.
Set `text_content=False` if the desired input for `page_content` is not a string
```

Use `text_content=True` (the default) only when the jq expression ends at a string, e.g. `.employees[].name`.

#### Useful `JSONLoader` parameters not used in the notebook

| Parameter | What it does | Example |
|---|---|---|
| `content_key` | Within each jq result, use **this key** as `page_content` instead of the whole object | `content_key='name'` → `page_content='John Doe'` |
| `metadata_func` | A function `(record, metadata) -> metadata` that copies fields from the record into metadata | see below |
| `json_lines` | Treat the file as JSON Lines (run the jq expression on each line) | `json_lines=True` |
| `is_content_key_jq_parsable` | Treat `content_key` as a jq expression too, for nested keys | `content_key='.projects[0].name'` |

`metadata_func` fixes the main weakness of Method 1, which is that its metadata is almost empty:

```python
def employee_metadata(record: dict, metadata: dict) -> dict:
    metadata["employee_id"] = record.get("id")
    metadata["role"] = record.get("role")
    return metadata

loader = JSONLoader(
    file_path='files/company_data.json',
    jq_schema='.employees[]',
    content_key='name',
    metadata_func=employee_metadata,
)
# → Document(page_content='John Doe',
#            metadata={'source': '...', 'seq_num': 1, 'employee_id': 1, 'role': 'Software Engineer'})
```

### Cell 8: Method 2, custom JSON processing

```python
from typing import List
from langchain_core.documents import Document

def process_json_intelligently(filepath: str) -> List[Document]:
    """Process JSON with intelligent flattening and context preservation"""
    with open(filepath, 'r') as f:
        data = json.load(f)

    documents = []

    # Strategy 1: Create documents for each employee with full context
    for emp in data.get('employees', []):
        content = f"""Employee Profile:
        Name: {emp['name']}
        Role: {emp['role']}
        Skills: {', '.join(emp['skills'])}

        Projects:"""
        for proj in emp.get('projects', []):
            content += f"\n- {proj['name']} (Status: {proj['status']})"

        doc = Document(
            page_content=content,
            metadata={
                'source': filepath,
                'data_type': 'employee_profile',
                'employee_id': emp['id'],
                'employee_name': emp['name'],
                'role': emp['role']
            }
        )
        documents.append(doc)

    return documents
```

**The idea:** instead of embedding raw JSON, **flatten** each employee (including the nested `skills` and `projects`) into a short, readable profile, and keep the identifying fields as metadata.

**Step by step:**
1. **`json.load(f)`** parses the file into a Python dict.
2. **`data.get('employees', [])`** returns an empty list if the key is missing, so a file without employees gives zero Documents instead of a `KeyError`.
3. **The f-string** writes the top-level fields as `Label: value` lines.
4. **`', '.join(emp['skills'])`** turns the list `["Python", "JavaScript", "React"]` into the text `Python, JavaScript, React`.
5. **The inner loop** turns each nested project object into a bullet line, so the projects stay *inside* their employee's Document. This is **context preservation**: the text "RAG System (Status: In Progress)" sits in the same chunk as "Name: John Doe", so a question like *"What is John working on?"* can be answered from one chunk.
6. **`metadata`** holds:
   - `source`: for citations,
   - `data_type: 'employee_profile'`: a label that lets you filter by record type once the index also has other kinds of Documents (departments, events, …),
   - `employee_id`, `employee_name`, `role`: for exact filtering and for linking back to the source record.

The comment says "Strategy 1" because the function is designed to grow: more loops (for `departments`, for example) can append other kinds of Documents to the same list. In the notebook only the employee strategy exists, so **`company` and `departments` are not included in any Document**.

#### The indentation gotcha
The triple-quoted f-string is indented inside the function, and **that indentation becomes part of the text**. The real `page_content` is:

```text
'Employee Profile:\n        Name: John Doe\n        Role: Software Engineer\n        Skills: Python, JavaScript, React\n\n        Projects:\n- RAG System (Status: In Progress)\n- Data Pipeline (Status: Completed)'
```

Note the 8 spaces before `Name`, `Role`, `Skills` and `Projects`, but not before the project bullets (those are added with `\n-`). It does not break anything, but it wastes tokens and adds noise to the embedding. Two clean ways to avoid it:

```python
import textwrap
content = textwrap.dedent(f"""\
    Employee Profile:
    Name: {emp['name']}
    ...""")

# or build it line by line:
lines = [
    "Employee Profile:",
    f"Name: {emp['name']}",
    f"Role: {emp['role']}",
    f"Skills: {', '.join(emp['skills'])}",
    "Projects:",
    *[f"- {p['name']} (Status: {p['status']})" for p in emp.get('projects', [])],
]
content = "\n".join(lines)
```

### Loading the JSONL file

```python
events = JSONLoader(

# → 3 Documents, e.g.
# page_content='{"timestamp": "2024-01-01", "event": "user_login", "user_id": 123}'
# metadata={'source': '...\\events.jsonl', 'seq_num': 1}
```

Or with plain Python, reading one line at a time (this works for files of any size):

```python
docs = []
with open('files/events.jsonl', encoding='utf-8') as f:
    for i, line in enumerate(f, start=1):
        if not line.strip():
            continue
        rec = json.loads(line)
        text = f"Event '{rec['event']}' by user {rec['user_id']} on {rec['timestamp']}"
        if 'page' in rec:
            text += f", page {rec['page']}"
        if 'amount' in rec:
            text += f", amount {rec['amount']}"
        docs.append(Document(page_content=text,
                             metadata={'source': 'files/events.jsonl', 'line': i, **rec}))
```

Putting `**rec` in metadata is fine here because every value is a simple type (string or number). Most vector stores do not accept nested lists or dicts as metadata values.

### Splitting at a deeper level without losing context
`.employees[].projects[]` gives one Document per project, but each one only says `{"name": "RAG System", "status": "In Progress"}`. The *owner* of the project is lost, so the question *"What is John working on?"* can no longer find it. The fix is to **copy parent fields down** into the child. With jq:

```python
JSONLoader(
    file_path='files/company_data.json',
    jq_schema='.employees[] | .name as $owner | .projects[] | {owner: $owner, project: .name, status: .status}',
    text_content=False,
)
```

or in Python, by looping over employees and then their projects and writing the employee's name into each project's text and metadata. The general rule: **every Document should make sense when read on its own.**

### Covering the departments
Following the "Strategy 1" pattern of the custom function, a second strategy could add one Document per department:

```python
for dept_name, dept in data.get('departments', {}).items():
    content = (f"Department: {dept_name.replace('_', ' ').title()}\n"
               f"Head: {dept['head']}\n"
               f"Budget: {dept['budget']:,}\n"
               f"Team size: {dept['team_size']}")
    documents.append(Document(page_content=content,
                              metadata={'source': filepath, 'data_type': 'department',
                                        'department': dept_name}))
```

Note that `.items()` keeps the department name, the same job `to_entries` does in jq.

### Generic flattening
For JSON whose shape you do not know in advance, a common approach is to flatten the tree into `path: value` lines:

```python
def flatten(obj, prefix=""):
    if isinstance(obj, dict):
        for k, v in obj.items():
            yield from flatten(v, f"{prefix}.{k}" if prefix else k)
    elif isinstance(obj, list):
        for i, v in enumerate(obj):
            yield from flatten(v, f"{prefix}[{i}]")
    else:
        yield f"{prefix}: {obj}"

# employees[0].name: John Doe
# employees[0].projects[1].status: Completed
# departments.engineering.budget: 1000000
```

Every value keeps its full path, so it never loses its meaning. The downside is that the text is less natural than a hand-written template, so use it as a fallback rather than the first choice.

## 5. Method Comparison

| | `JSONLoader` + `jq_schema` | Custom Python processing |
|---|---|---|
| **Code needed** | A few lines | A function per record type |
| **Choosing records** | jq expression (very flexible, but another language to learn) | Python loops |
| **`page_content`** | Raw JSON text (or one key with `content_key`) | Any text format you design |
| **Metadata** | `source` + `seq_num`; more only with `metadata_func` | Anything you want |
| **Parent context in child records** | Possible with jq variables (`as $x`) | Easy: you are already inside the parent loop |
| **JSON Lines** | `json_lines=True` | Read and `json.loads` line by line |
| **Extra dependency** | `jq` package | None |
| **Best for** | Quick loading, large or uniform files, a fixed schema | Production RAG where retrieval quality matters |

**Rule of thumb:** use `JSONLoader` to explore data and get a baseline quickly. Move to custom processing (or `JSONLoader` with `content_key` + `metadata_func`) once you know which questions users will ask and need the text and metadata shaped for them.

## 6. Using the Output in a RAG Pipeline

Both methods return a `List[Document]`, so the next steps are the same:

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_community.vectorstores import FAISS

docs = process_json_intelligently('files/company_data.json')

# Optional: these profiles are short, so splitting usually isn't needed.
# Only split records that are longer than your chunk size.
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)

embeddings = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")
store = FAISS.from_documents(chunks, embeddings)

store.similarity_search("Who knows machine learning?", k=1)
# → Jane Smith's profile

store.similarity_search("projects in progress", k=2, filter={"role": "Software Engineer"})
# → semantic search limited by an exact metadata filter
```

Tips for JSON sources:
- **Prefer one meaningful record per Document** (an employee, a product, an event) over fixed-size chunks of raw JSON. A text splitter that cuts JSON in the middle produces chunks like `"status": "In Progress"}, {"name":` that mean nothing.
- **Keep metadata values simple** (strings, numbers, booleans). Lists and nested dicts are rejected or ignored by many vector stores.
- **Questions that need counting or totals** (*"total budget of all departments"*) are answered badly by vector search alone. Either index pre-computed summaries, or let the LLM query the JSON with code instead.

## 8. Quick Glossary

| Term | Meaning |
|---|---|
| **JSON** | Text format for nested data made of objects (`{}`), arrays (`[]`) and simple values |
| **JSON Lines / JSONL** | One JSON object per line; easy to append to and to stream |
| **Serialize / deserialize** | Python object → JSON text (`json.dump(s)`) / JSON text → Python object (`json.load(s)`) |
| **jq** | Query language for selecting parts of JSON; used by `JSONLoader` via `jq_schema` |
| **`jq_schema`** | The jq expression that decides what becomes a Document; each result = one Document |
| **`text_content`** | `JSONLoader` flag: `True` expects string results; `False` allows objects (serialized to JSON) |
| **`content_key`** | `JSONLoader` option: use this key of each result as `page_content` |
| **`metadata_func`** | `JSONLoader` hook that copies record fields into metadata |
| **`seq_num`** | `JSONLoader` metadata: 1-based position of the record among jq results |
| **Flattening** | Turning a nested JSON record into flat text or key-value lines |
| **Context preservation** | Keeping parent information (e.g. employee name) with child data (e.g. projects) in the same Document |
| **Document** | LangChain object with `page_content` (embedded text) and `metadata` (filterable fields) |
